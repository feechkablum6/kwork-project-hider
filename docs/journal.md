## 2026-08-02

Пользователь сообщил, что лента после входа несколько раз меняет верхний проект с интервалом три-четыре секунды. Живой прогон логики расширения на `kwork.ru/projects?c=45` воспроизвёл причину: право на объединение проверялось строковым сравнением подписи полей запроса, а подпись собственной сборки строится из адреса страницы. Когда набор полей Kwork отличался от параметров адреса (`c=45` против `c=45&sort=1`), ответ на собственный клик расширения не объединялся — Kwork рисовал настоящую следующую страницу, расширение начинало вторую сборку и через две секунды подменяло ленту снова. В трассировке это выглядело как `renderMerged=false` → `12 карточек` → `renderMerged=true` → `138 карточек`.

Клик итоговой отрисовки теперь объявляется событием `kph-feed-render`, и первый запрос `/projects` в течение трёх секунд после него получает объединённую ленту независимо от набора полей. Чтобы принудительное объединение не подменило выдачу чужого фильтра, стартовая сборка по адресу сверяет первую собранную страницу с проектами, уже показанными в DOM: при совпадении меньше половины идентификаторов расширение отдаёт `kph-feed-limited` и оставляет штатную пагинацию.

Повторный живой прогон: расхождение полей больше не даёт промежуточной перерисовки (`renderMerged=true`, 138 карточек с первого клика), а сборка чужой категории (`c=41` поверх показанной ленты `c=45`, совпадение `0/12`) возвращает пагинацию Kwork и не трогает ленту.

Затем пользователь сообщил о пустом экране при заходе. Трассировка на его аккаунте (`kwork.ru/projects?a=1`, все рубрики любимые, десять страниц выдачи) дала тайминги: список Kwork появляется на 1469 мс, скрытие карточек срабатывает на 1914 мс и оставляет две карточки из двенадцати, событие `kph-feed-start` приходит только на 1682 мс, фоновая сборка стартует по секундной паузе на 2694 мс, а объединённая лента из 118 карточек показывается на 5086 мс. То есть больше трёх секунд экран оставался почти пустым — не из-за ошибки объединения, а потому что первая страница пользователя скрыта почти целиком.

Фоновая сборка перенесена на установку перехватчика в MAIN world: она больше не ждёт готовности DOM и секундной паузы, пауза осталась только для сборок по запросам Kwork при смене фильтра. Готовность объединённой ленты публикуется атрибутом `data-kph-feed-collected`, поэтому content script подхватывает её, даже если сборка закончилась раньше его запуска. Сверка собранной ленты с показанными проектами перенесена из сборки в момент запроса на отрисовку и отвечает атрибутом `data-kph-feed-render`: без разрешения клик по пагинации не выполняется, поэтому чужая выдача не подменяет ленту и не уводит пользователя на вторую страницу.

Замер после переноса: сборка стартует на 792 мс вместо 2694 мс, объединённая лента показывается на 4370 мс вместо 5086 мс, а окно без единого видимого проекта сократилось с 3,2 до 1,9 секунды. Параллельность фоновых запросов поднята с трёх до пяти; дальнейший выигрыш упирается в сами запросы (2,4 секунды на десять страниц) и отрисовку 117 карточек силами Kwork (около секунды).

Затем пользователь заметил, что первая страница около полусекунды показывает уже скрытые карточки. Причина в моменте запуска: скрытие жило в наборе content scripts с `run_at: document_idle`, то есть включалось после отрисовки ленты Kwork (список на 1469 мс, скрытие на 1914 мс).

Перенос набора на `document_start` сначала выключил расширение целиком: диагностический маркер показал `core=false`. Chrome не подключает один и тот же файл к двум наборам content scripts с одинаковым `run_at`, поэтому `src/core.js` доставался только MAIN world, а изолированный оставался без ядра и выходил на первой же проверке. Проверка с копией файла подтвердила причину: изолированный мир получает ядро отдельным файлом `src/core-isolated.js`, который создаётся командой `npm run sync-core`, а тест сверяет копию с исходником, чтобы они не разъехались.

Заодно инициализация скрытия стала устойчивой: наблюдатель за лентой подписывается до ответа `chrome.storage`, найденные раньше карточки скрываются после его получения, а уведомление не пытается вставить себя в ещё не существующий `body`. Единая лента больше не зависит от порядка запуска скриптов: если атрибута `data-kph-feed-ready` ещё нет, она ждёт события `kph-feed-ready`.

Живая проверка версии 1.3.3 на аккаунте пользователя: карточки Kwork появляются на 2083 мс уже отфильтрованными (12 карточек, видно 3 — скрытие сработало в том же кадре), объединённая лента приходит на 3047 мс.

Оставшееся ожидание закрыто контурами карточек: пока идёт сборка или отрисовка и в ленте нет ни одного видимого проекта, в `.project-list` появляются три заполнителя по геометрии карточки Kwork. Состояние сборки публикуется атрибутом `data-kph-feed-collecting`, поэтому content script показывает контуры и тогда, когда сборка началась раньше его запуска. Живая проверка на аккаунте пользователя: карточки скрываются на 3049 мс, контуры (234×804 px против настоящих 238×804) стоят до 4117 мс и исчезают вместе с приходом объединённой ленты.

## 2026-08-06 — выгрузка переписок с клиентами на диск

Задача: агент должен получать полную переписку с клиентом одной командой, без браузера и без входа в аккаунт.

Поиск готовых решений результата не дал: расширений и юзерскриптов для экспорта переписок Kwork не существует (на Greasy Fork нет ни одного скрипта под kwork.ru), MCP-серверов под биржу тоже нет. Есть только обёртки над закрытым мобильным API — `kesha1225/kwork` (Python, PyPI `kwork`) и `CrazyMan-IK/kwork-api` (Node.js) с методами `dialogs`, `inboxes`, `inboxCreate`; обе авторизуются логином и паролем, а не сессией браузера, и сам автор библиотеки предупреждает, что часть вызовов идёт через недокументированные веб-эндпоинты и может сломаться.

Выбран путь поверх уже авторизованной вкладки: расширение читает то, что биржа и так отдаёт странице, и складывает результат на диск. Сообщения ищутся по структуре ответа, а не по адресу запроса, — доступа к живому Kwork на момент разработки не было, и привязка к конкретным эндпоинтам сделала бы разбор ложно точным. Шаблон запроса для догрузки старой истории берётся из перехваченного запроса и повторяется с увеличенным номером страницы, как это уже сделано для ленты проектов.

Запись на диск — native messaging: `chrome.downloads` умеет писать только внутрь папки загрузок, а File System Access API в MV3 требует открытого окна расширения для повторного запроса разрешения (Chromium issue 40240444). Мост на Node.js пишет в любую папку; по умолчанию `F:\Projects\Kwork\переписки`.

Установщик сначала не находил расширение: `extensions.settings` Chrome хранит в `Secure Preferences`, а не в `Preferences`. После правки идентификатор нашёлся (`dmjgcghiepiaeacpamgadcdmckihnnbo`), и вычисление идентификатора из пути (sha256 в UTF-16LE) дало тот же результат — оно осталось запасным вариантом на случай, когда расширение ещё не загружено в браузер.

Сквозная проверка моста без браузера: кадр протокола, поданный в `native_host/kwork-bridge.bat`, вернул `{"ok":true}` и создал `переписки/proverka_mosta.md` с ролями и вложениями; `scripts/kwork-chat.mjs` по ссылке `https://kwork.ru/inbox/proverka_mosta` напечатал переписку. Тестовые файлы удалены после проверки.

Открытые места: сами файлы-вложений пока не скачиваются (в переписке остаются имена и ссылки), а обход диалогов без их открытия появится после первых образцов реальных ответов Kwork — они сохраняются в `data/<клиент>.json`.

## 2026-08-06 — полная история переписки и массовая выгрузка

Пользователь сообщил, что выгруженная переписка неполная. Причина в контракте биржи: `/inbox_more_messages` отдаёт последние 50 сообщений на запрос, а в перехваченном теле запроса нет ни одного параметра пагинации — только `userId`, `allUnread` и `limit`. Прежняя догрузка искала `page`, `offset`, `skip` и `p`, не находила их и не листала вовсе; 117 сообщений накопились лишь потому, что пользователь сам прокручивал переписку и каждый запрос страницы перехватывался.

Код чата лежит в бандле страницы `/inbox`, доступной только после входа, поэтому имя параметра из публичных файлов Kwork получить не удалось: в `general`, `vue`, `common-top` его нет, а в `header` встречаются только ссылки на `/inbox/support`. Вместо угадывания в ядро добавлен подбор: `buildHistoryProbes` формирует кандидатов (увеличенный `limit`, затем `offset`, `skip`, `page`, затем курсоры по идентификатору самого старого сообщения), обходчик пробует их на живом запросе и запоминает первый, вернувший новые сообщения. Стратегия переиспользуется до конца диалога, а отсутствие новых сообщений означает, что история прочитана целиком.

Массовая выгрузка сделана в два прохода. Быстрый: список диалогов со страницы переписок, для каждого известного собеседника история читается прямыми запросами. Медленный: диалоги, которые никогда не открывались, идентификатора клиента не имеют, поэтому фоновый скрипт открывает их по одному в своей вкладке, дожидается перехваченного ответа с `conversationUserId` и дочитывает историю тем же способом. Оба прохода пишут в мост, а слияние по идентификаторам сообщений исключает дубли при повторных запусках.

Попап собран на палитре расширения: белая поверхность, фирменный зелёный на основной кнопке, полоса прогресса 6 px. Пока собирается список, длина неизвестна, поэтому полоса движется циклом; дальше она показывает долю пройденных диалогов через `transform: scaleX`. Тексты состояний считает `popup-view.js` — отдельный тестируемый модуль, включая согласование числительных.

### Почему история обрывалась на первой пачке

Первый прогон массовой выгрузки дал 48 сообщений на диалог и одну переписку из полутора десятков. Разбор показал две независимые причины.

История останавливалась на первом запросе: `loadDialogHistory` считала переписку прочитанной, если получено меньше `limit` сообщений. Kwork отдаёт пачку в 50 записей, часть которых повторяется, и после дедупа остаётся 48 — проверка срабатывала всегда, листание не начиналось ни разу. Признаком конца теперь служит только отсутствие новых сообщений в ответах всех вариантов запроса. Сработавший вариант и признак полноты пишутся в JSON диалога.

Список переписок собирался лишь из ссылок разметки, которых на странице не оказалось: единственный ключ пришёл из памяти расширения. Добавлены ещё два источника — разметка ответа `/inbox` и состояние страницы, — а пробные запросы к возможным адресам списка сокращены до одной страницы на адрес. Диагностика (адрес вкладки, число ссылок, ответы проб) теперь сохраняется всегда, а не только при полном нуле, иначе разбирать нечего.

Заодно поправлен итог в попапе: «Сохранено: 1 переписка, 48 сообщений» читалось как весь объём, хотя это добавленное за проход. Теперь пишется «Обработано N переписок, добавлено M сообщений».

### Ускорение массовой выгрузки

Выгрузка шла последовательно: диалог за диалогом, страница за страницей, с паузой 250 мс между запросами, а для каждого неоткрытого диалога фоновый скрипт открывал страницу переписки в вкладке и ждал полной загрузки — несколько секунд на диалог.

Ключевая находка: страница профиля `/user/<ник>` содержит `"userProfileId":<id>,"userProfileName":"<ник>"`, то есть идентификатор клиента доступен одним запросом без открытия диалога. Проверено на публичной странице `kwork.ru/user/sobolevs`.

Что изменилось: идентификаторы разрешаются заранее пачкой по шесть параллельных запросов; диалоги обрабатываются по четыре одновременно; страницы истории, которые листаются смещением, забираются пачками по четыре (курсорные варианты остаются последовательными, потому что зависят от предыдущего ответа); пауза между запросами снижена с 250 до 60 мс, пауза между диалогами убрана. Навигация по вкладке осталась запасным путём для диалогов, чей профиль не открылся.

### Проверка выгруженных переписок: чужие сообщения в файлах

Аудит 21 выгруженного диалога показал загрязнение данных. В `sobolevs.json` оказалось 1658 сообщений от 21 разного автора — то есть сообщения всех переписок сразу, при том что собственных у диалога 473. В `13bis.json` лежало по одному сообщению от каждого собеседника, то есть срез списка диалогов.

Причина в контракте биржи: `/inbox_more_messages` вызывался с `allUnread=true`, а стратегия листания «увеличенный limit» доводила лимит до тысяч. На таком запросе Kwork возвращает сводную ленту по всем перепискам, а не диалог с указанным `userId`.

Исправлено на уровне данных, а не параметров запроса: сообщение принимается в диалог, только если один из его участников — клиент этого диалога. Для этого при разборе сохраняются получатель (`mto`, `MSGTO`) наряду с отправителем, а `filterDialogMessages` применяется в трёх местах: в обходчике, в перехватчике страницы и в мосте при слиянии с уже сохранённым файлом. Последнее важно: повторная выгрузка вычищает ранее записанный мусор без ручного удаления файлов. Дополнительно `allUnread` переведён в `false`, а рост лимита ограничен 300 сообщениями.

Попутно из списка убраны служебные диалоги (`support`, `kwork`, `admin`) и собственный профиль: страница профиля отдаёт `isSameUser: true`, по этому признаку он отсеивается. Пустой файл собственного профиля удалён.

Остальные 18 переписок аудит прошли чисто: два участника, полные даты, корректные роли, ни одного сообщения без времени или автора.

### Повторная проверка после чистой выгрузки

Загрязнение ушло: во всех переписках ровно два участника. Осталось три дефекта, найденных аудитом.

### 2026-08-06. Файлы переписки скачиваются на диск, папка на диалог

Вложений в сохранённых данных было ноль, хотя в переписках они есть. Причина в разборе: Kwork отдаёт файлы сообщения двумя полями сразу — списком `filesArray` и словарём `files`, где ключ это идентификатор файла. Разбор ждал массив, получал словарь и молча его отбрасывал. Теперь понимает обе формы, схлопывает повторы по идентификатору и берёт имя из поля файла либо из адреса, где кириллица закодирована процентами.

Скачивание отдано вкладке Kwork. Пробный запрос к вложению без кук возвращает страницу ошибки, а из фонового скрипта нельзя подставить адрес страницы в `Referer`. Вкладка же качает файл ровно как браузер. Дальше файл идёт кусками по 3 МБ в base64 через фоновый скрипт в мост: `save-attachment` копит куски во временном файле и переименовывает готовое вложение. Мост отвечает на команды с эхом идентификатора запроса, поэтому расширение может спросить у него список уже сохранённых файлов (`list-attachments`) и не качать их повторно.

Имена вложений считаются по всему диалогу сразу (`resolveAttachmentFiles`): каждый скриншот приходит как `image.png`, и без общего пересчёта файлы затирали бы друг друга. Тёзки разводятся номером, одно и то же вложение всегда получает одно имя, поэтому ссылки в markdown стабильны между выгрузками.

Раскладка папки переписок переехала на папку с диалогом: `<ник>/переписка.md`, `<ник>/данные.json`, `<ник>/файлы/`. Служебные `_dialogs.json` и `_diagnostics.json` остались в `data/`. Мост переносит старые плоские файлы сам, 19 сохранённых переписок перенесены.

Вложения появятся в данных только после новой выгрузки: у сохранённых ранее сообщений поле вложений пустое, а слияние берёт непустой вариант.

Первая выгрузка с вложениями показала два дефекта. На диске оказалось 243 файла против 130 в данных, а размеры сохранённых картинок не совпадали с заявленными.

В текст диалога сообщения не попадали (мост фильтрует повторно по сохранённому идентификатору), а вот файлы качались из необработанной порции и ложились в чужую папку: голосовые из майской переписки оказались в июльской.
