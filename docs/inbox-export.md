# Выгрузка переписок Kwork на диск

Переписки с клиентами сохраняются в обычные файлы на диске, чтобы ИИ-агент читал их одной командой, без браузера и без входа в аккаунт.

## Как устроено

1. `src/inbox-main.js` в MAIN world слушает ответы Kwork на страницах `/inbox` и `/new_inbox` (XHR и `fetch`). Сообщения распознаются по структуре ответа, а не по адресу запроса, поэтому смена внутреннего API биржи не ломает выгрузку целиком.
2. Найдя историю сообщений, перехватчик запоминает шаблон запроса и через паузу в 800 мс дотягивает остальные страницы истории — те, что в интерфейсе видны только после прокрутки вверх.
3. `src/inbox-content.js` в изолированном мире склеивает сообщения без дублей и отдаёт их фоновому скрипту.
4. `src/background.js` передаёт данные native messaging хосту `ru.kwork.hider.host`.
5. `native_host/kwork-bridge.js` пишет папку на каждый диалог — `переписка.md`, `данные.json` и подпапку `файлы/` — и накапливает историю между сессиями.

Расширение ничего не отправляет наружу: данные идут из вкладки Kwork в локальный файл.

## Автосохранение

Кнопку нажимать не нужно: фоновый скрипт держит живой канал Kwork (веб-сокет `notice.kwork.ru`, адрес канала — из `pullModuleSettings` страницы `/inbox`, только в памяти) и по событию `new_inbox`/`inbox_sent` сразу делает проход; раз в минуту будильник `chrome.alarms` делает проход на случай обрыва канала. Фоновый скрипт сам запрашивает страницу `/inbox` с куками пользователя, вкладка Kwork для этого не нужна. На странице есть готовый список 50 последних диалогов `window.chatList` с последним сообщением каждого (`parseChatList`). Диалог, у которого последнее сообщение не изменилось с прошлого прохода, не трогается; идентификаторы последних сообщений — не переписка, они лежат в `chrome.storage` (`inboxSyncSeen`).

По изменившемуся диалогу берётся последняя страница истории (50 сообщений) и дописывается в папку диалога через мост. Новый диалог или диалог с пропуском — самое старое из пришедших новее последнего сохранённого (`needsFullHistory`) — дочитывается целиком тем же листанием, что и ручная выгрузка (`loadDialogHistory` в ядре). Недостающие вложения качает сам фоновый скрипт: мост сверяет всю сохранённую переписку с папкой `файлы/` (`missing-attachments`), раз в час обходит все диалоги с недокачанным (`dialogs-missing-files`). Файл, который не скачался пять раз, больше не пробуется (`inboxFileRetries`): так бывает с HEIC и webp, вместо которых Kwork отдаёт уменьшенную JPEG-копию другого размера. Файлы «Сообщений» Kwork хранит в `kwork-conversation.storage.yandexcloud.net`, файлы из чата заказа — в `kwork-track.storage.yandexcloud.net`.

Сорвавшийся диалог (429, обрыв, мост не ответил, история дочитана не до конца) не отмечается просмотренным и повторяется с растущей паузой — 2, 4, 8… минут, не реже раза в час (`inboxSyncRetries`). Пока такие есть, `_sync.json` пишет `ok: false` и их список в `pending`. Ответ 429 или сбой сервера останавливает весь проход: оставшиеся диалоги, файлы и отклики ждут 10 минут (`pausedUntil`) и числятся недочитанными. Отклики (`/offers`) тянутся раз в 6 минут; отметки времени лежат в `chrome.storage` (`inboxSyncTimes`), потому что фоновый скрипт засыпает между проходами.

Итог прохода ложится в `data/_sync.json`: время, ошибка, какие диалоги обновились и какие ещё не дочитаны. По нему хук агента сообщает, насколько свежи данные, а попап показывает строку «последний раз в 12:41». Вышли из аккаунта — проход ничего не пишет в переписки, только отметку «вход не выполнен».

## Установка моста

```bash
node scripts/install-bridge.mjs
```

Или двойным щелчком: `install.bat` в Windows, `install.command` в macOS. Первым аргументом можно задать другую папку:

```bash
node scripts/install-bridge.mjs "F:\Projects\Kwork\переписки"   # Windows
node scripts/install-bridge.mjs ~/Projects/Kwork/переписки          # macOS
```

Установщик находит идентификатор расширения в профилях Chrome, Chromium и Edge и создаёт папки переписок и заказов. В Windows манифест хоста лежит в `%LOCALAPPDATA%\KworkProjectHider` и прописывается в реестр `HKCU`; в macOS реестра нет, поэтому манифест кладётся в папку `NativeMessagingHosts` каждого установленного браузера. После установки Chrome нужно перезапустить.

Запуск моста собирается там же в виде маленькой программы `kwork-bridge.exe` (компилируется штатным `csc.exe` из .NET Framework): Chrome 151 запускает native messaging host только настоящим исполняемым файлом, а командный файл отклоняет, отвечая расширению «мост не найден».

В macOS ту же роль играет `kwork-bridge.sh` в `~/Library/Application Support/KworkProjectHider`. Chrome запускает мост с системным `PATH`, в котором нет Node из Homebrew, поэтому путь к Node записан в запускателе целиком, а поиск по `PATH` остаётся запасным путём после обновления Node.

Путь к папке хранится в `native_host/bridge-config.json` — файл локальный и в git не попадает.

## Что появляется на диске

```
переписки/
  ivan_petrov/
    переписка.md          — читаемый диалог
    данные.json           — сообщения, вложения и образцы ответов биржи
    файлы/                — скачанные вложения и скриншоты
      макет.png
      техзадание.docx
  data/
    _dialogs.json         — список известных диалогов
    _diagnostics.json     — срез страницы, если список собрать не удалось
```

Markdown содержит шапку с ссылкой, числом сообщений и числом файлов, дальше сообщения по времени с подписью «Я» или именем клиента. Вложения идут ссылками на скачанные файлы в папке «файлы», поэтому открываются прямо из текста переписки. Роли определяются по идентификатору собеседника из ответа биржи.

Сообщение, отправленное кнопкой «Ответить», начинается с цитаты исходной реплики:

```
## Я — 05.08.2026, 13:19 МСК

> В ответ на сообщение «Hr_pro — 05.08.2026, 11:39 МСК»:
> 17450 все комплекты стоимость

Шесть комплектов опубликованы
```

Подпись в кавычках повторяет заголовок исходного сообщения слово в слово, поэтому и человек, и ИИ-агент находят его простым поиском по тексту. В `данные.json` та же связь лежит в поле `replyTo` сообщения: идентификатор, автор, время и текст процитированной реплики. Переписки, сохранённые до версии 1.13.0, дополняются связями при следующей выгрузке.

JSON хранит те же сообщения в исходном виде плюс до трёх образцов сырых ответов Kwork вместе с параметрами запроса — по ним уточняется разбор, если биржа поменяет формат.

Переписки, сохранённые до версии 1.10.0, лежали плоско (`ivan_petrov.md` и `data/ivan_petrov.json`). Мост переносит их в папку диалога сам при первом же обращении.

Формат подтверждён на живой переписке: историю отдаёт `/inbox_more_messages`, отправитель приходит в `MSGFROM` и `mfrom`, собеседник — в `params.conversationUserId`. Разбор опирается на эти поля, но не требует их: при переименовании сообщения всё равно находятся по структуре.

## Выгрузка всех переписок

Значок расширения открывает попап с кнопкой «Извлечь все переписки». Порядок работы:

1. Фоновый скрипт находит открытую вкладку Kwork или открывает `https://kwork.ru/inbox` сам и проверяет доступ: если биржа увела вкладку на вход, выгрузка не начинается, а попап предлагает открыть Kwork.
2. Список переписок дожидается отрисовки и прокручивается до конца, потому что Kwork подгружает его порциями.
3. `src/inbox-crawler.js` собирает список диалогов: ссылки на странице переписок плюс ответы биржи, если их удалось получить запросом.
4. Для каждого диалога с известным идентификатором клиента история читается напрямую пачками по 50 сообщений, пока приходят новые.
5. Идентификаторы клиентов берутся со страниц профилей (`/user/<ник>`, поле `userProfileId`) пачкой по шесть запросов. Диалоги обрабатываются по четыре одновременно, а страницы истории со смещением — пачками по четыре. Диалоги, чей профиль не открылся, фоновый скрипт дочитывает по одному через свою вкладку.
6. Каждый диалог уходит в мост и сливается с уже сохранённым файлом по идентификаторам сообщений, поэтому повторный запуск не создаёт дублей.

Прогресс виден в попапе: номер диалога, общее число диалогов и накопленное число сообщений. Выгрузку можно остановить кнопкой и продолжить позже.

### Файлы и скриншоты

Kwork отдаёт вложения сообщения двумя полями сразу: списком `filesArray` и словарём `files` по идентификатору файла. Разбор читает оба и схлопывает повторы, а имя берёт из поля файла либо из адреса, где кириллица закодирована процентами.

При ручной выгрузке файлы скачивает вкладка Kwork, при автосохранении — фоновый скрипт: ссылка ведёт на kwork.ru и переадресуется в хранилище `kwork-conversation.storage.yandexcloud.net`, на которое у расширения есть разрешение. Дальше файл идёт кусками по 3 МБ в base64 через фоновый скрипт в мост, тот копит их во временном файле и переименовывает готовое вложение под настоящим именем.

Имена вложений на бирже повторяются: каждый скриншот приходит как `image.png`, голосовые называются числом. Поэтому имя файла строится из даты и времени сообщения по Москве плюс исходное имя — `2026-08-05 11-26-50 image.png`. Такое имя осмысленно, сортируется по возрастанию и не зависит от того, какие сообщения пришли в этой порции: раньше имена считались по набору сообщений, и при частичной выгрузке один файл затирал другой. Два вложения одного сообщения с одинаковым именем разводятся номером. Повторная выгрузка не перекачивает файлы: мост отдаёт список уже сохранённых вложений с размерами, и совпадающие пропускаются.

Сообщение попадает в переписку только по именам участников, если они есть в ответе. Идентификатор собеседника для этого не годится: страница открытого диалога видит и запросы соседних диалогов, а идентификатор берётся из того же ответа и подтверждал бы чужую переписку сам себе — чужие вложения уезжали в чужую папку.

Диалоги самой биржи (`Support`, `Kwork`, `admin`) перепиской с клиентом не считаются: они не выгружаются, не попадают в список известных диалогов и не сохраняются даже при ручном открытии такого диалога в браузере. Собственный профиль исключается по второму участнику первой же переписки.

### Если список собрать не удалось

Расширение складывает срез страницы в `data/_diagnostics.json`: адрес вкладки, число найденных ссылок, первые двадцать адресов и ответы пробных запросов. По этому файлу разбирается причина без доступа к браузеру.

### Как ищется параметр листания

Kwork отдаёт последние 50 сообщений и не публикует, чем листать глубже. `buildHistoryProbes` формирует кандидатов: увеличенный `limit`, затем `offset`, `skip`, `page`, затем курсоры по идентификатору самого старого известного сообщения. Первый вариант, вернувший новые сообщения, запоминается и используется до конца диалога. Если ни один не дал нового, история считается прочитанной полностью.

## Чтение переписки агентом

```bash
node scripts/kwork-chat.mjs https://kwork.ru/inbox/ivan_petrov
```

Команда печатает переписку в stdout. Дополнительно:

- `--json` — выдать полные данные вместо markdown;
- `--list` — показать сохранённые переписки;
- вместо ссылки принимается ник клиента или его часть.

Если переписка ещё не сохранена, команда сообщает об этом и предлагает открыть диалог на бирже.

## Третья галочка «есть у Claude»

У каждого сообщения на `/inbox/<ник>` и в чате заказа `/track` рядом с галочками Kwork стоит оранжевая галочка, если сообщение уже лежит на диске и его видит агент. Подсказка при наведении — «Есть у Claude: сообщение сохранено на диск». У сообщения клиента она одна, у своих — третья после двух зелёных.

Сообщение на странице и на диске сопоставляются по ключу «автор:время в секундах» (`messageKey` в ядре): идентификаторы страницы и истории у Kwork разные. Данные сообщения лежат в компоненте Vue, поэтому ключ ставит MAIN world (`src/ticks-main.js`, атрибут `data-kph-key`), а галочку — изолированный `src/ticks-content.js` по списку ключей от моста (`message-keys`). Новое сообщение получает галочку через несколько секунд после сохранения: неотмеченные блоки перепроверяются раз в 10 секунд. Диалог на странице заказа определяется по второму участнику из `window.userAvatarColors` — так он известен и до первого ответа клиента.

## Сводка для агента и сверка «отправлено»

Хук `~/.claude/scripts/kwork-chat-brief.sh` (SessionStart и UserPromptSubmit) запускает `scripts/kwork-brief.mjs`. В чате заказа из `~/Projects/Kwork/Активные/<заказ>` — и в его рабочей копии T3 — агент получает: кто писал последним и сколько ждёт клиент, в начале сессии шесть последних сообщений, дальше только новые (до 12 за раз, целиком, а не влезшие в объём называются числом), пути к файлам клиента; время — по часам мака, как его показывает Kwork; файл, который ещё качался, сообщается отдельно, когда ляжет на диск. В корне `~/Projects/Kwork` — клиенты, которые ждут ответа. Автосохранение давно не шло или упало — первой строкой предупреждение. Заказ связан с ником строкой в `~/Projects/Kwork/docs/заказы-клиенты.md` или ссылкой `kwork.ru/inbox/<ник>` в CLAUDE.md заказа.

Stop-хук `~/.claude/scripts/kwork-draft-capture.sh` запускает `scripts/kwork-drafts.mjs capture`: из последнего хода агента (после настоящего сообщения пользователя) вынимаются черновики с маркерами — «Сообщение/Текст/Ответ/Черновик … клиенту:», `Цена:` + `Срок:`, `Название заказа:` — и каждый ложится отдельным файлом в `~/.claude/skills/estimate/data/pending/`. Только в чатах Kwork.

Сверка (`sync`, запускается и Stop-хуком, и перед каждой сводкой) под замком-папкой ищет отправку:

- сообщение и цена — исходящее «Я» в переписке клиента заказа не раньше чем за 2 минуты до черновика и не позже 3 суток, по совпадению слов (не меньше 60 % слов отправленного есть в черновике, и отправка покрывает не меньше 30 % черновика) или той же цене; без известного клиента — только почти дословно (80 %) по всем диалогам. Подряд идущие похожие исходящие в 15 минут склеиваются, пока не ответил клиент. `Цена:` и `Срок:` рядом с сообщением клиенту — числа того же черновика, а не второй; Одно сообщение закрывает только один черновик (`sent-claimed.json`);
- отклик — по номеру проекта в `data/_offers.json`, иначе по тексту; засчитывается только отклик, появившийся или изменившийся после черновика (снимок откликов при захвате); цена и срок берутся с биржи, текст сравнивается без строк цены и срока.

Итог — строка в `sent.md` с пометкой «(авто)»: дословно или с правками, какая цена и срок ушли на самом деле. Строка пишется до удаления черновика и проверяется по метке `draft <id>`, поэтому сбой между шагами не даёт дубля. «Не отправлено» пишется только когда автосохранение прошло позже конца окна и диалог клиента не в списке недочитанных; черновик без цены и срока, который так и не ушёл, снимается без строки.

## Ограничения

- Нужен запущенный Chrome с выполненным входом в Kwork: расширение работает с той сессией, которая уже авторизована в браузере. Пока Chrome закрыт или мак спит, автосохранение стоит.
- Автосохранение видит 50 последних диалогов со страницы `/inbox`; старые диалоги дописываются ручной выгрузкой.
- Уже сохранённые вложения повторно не качаются.
- Список диалогов обходчик (`src/inbox-crawler.js`) прокручивает сам до конца, потому что Kwork подгружает его порциями, и собирает ссылки за один запуск.

## Тихое чтение непрочитанного

`/inbox_more_messages` отмечает сообщения прочитанными. Поэтому диалог, у которого в списке `/inbox` есть непрочитанное (`unread_count > 0`), фоновый скрипт читает через `/api/inbox/getnewmessages` (`interlocutorId`, `lastMessageId`): так сайт Kwork сам подтягивает новые сообщения в открытый чат, а прочитанными их отмечает отдельный `/api/inbox/readmessages`, когда вы их увидели. Первый тихий запрос идёт с `lastMessageId=0` и приносит всю переписку без сообщений внутри заказа, дальше — только новее сохранённого MID (`inboxSyncQuietMids`). Курсор не уходит за первое непрочитанное сообщение клиента: следующий запрос снова вернёт его с текущей отметкой, поэтому признак личного непрочитанного (`clientUnread`) держится, пока вы его не прочитали. Номер такого сообщения — MID; при склейке с обычной выгрузкой он остаётся. Тихая запись снимает подтверждение полноты истории (`complete: false`): сообщения заказа между старым и новым временем не читались, и обычный путь потом дочитает историю целиком. Диалог отмечается `unread:<MID списка>` и не перечитывается, пока клиент не написал ещё; когда вы прочитали его на Kwork, он дочитывается обычным путём.

Сообщений внутри заказа getnewmessages не отдаёт, а `unread_count` их считает. Последнее в диалоге — сообщение заказа (`type: 'track'` в списке, поле `order`) — после тихого чтения идёт и обычная выгрузка: сообщения заказа она прочитанными не отмечает (лог kwork-hunter 16.10.2026: unread заказа stroisnab2007 держался 26 минут после выгрузки). Если при этом у клиента есть личное непрочитанное (`clientUnread`), обычная выгрузка отметила бы его — тогда диалог отложен (`held`) до вашего прочтения, а личное уже на диске. Обычная выгрузка не начинается и тогда, когда канал сообщил о новом сообщении клиента уже после снимка списка (`forcedNext`): unread в снимке устарел, диалог берёт следующий проход.

## Побудка агента и Telegram

Новое сообщение клиента будильщик моста (`native_host/waker.js`) отдаёт агенту в чат T3 заказа. Telegram (очередь `data/outbox`) получает его, только когда пользователь не работает с агентом: в чате, куда пришла побудка, пользователь сам писал не позже часа назад (`ENGAGED_MS`, `isEngaged` в `wake-core.js`) — тогда сообщение идёт только агенту, а побудка помечена строкой `QUIET_MARK`, и Stop-хук `kwork-wake-report` итог агента в Telegram не шлёт. Settled-чат или час тишины — снова Telegram, но только с сообщениями, которых агент ещё не получал. Не дошло до агента (T3 закрыт, сбой) — Telegram страхует сразу. Тихая побудка кладёт в очередь запись `quiet: true`: робот kwork-hunter в Telegram её не шлёт, а только отмечает сообщения доставленными, иначе его собственная проверка «не прочитано 5 минут» прислала бы их сама.
